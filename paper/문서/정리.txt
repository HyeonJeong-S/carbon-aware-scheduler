[1] 한 줄 결론
----------------------------------------------------------
KCI 투고 가능하다. 지금 필요한 건 새 실험이 아니라 논증 수정이다.

참고 논문 4편을 원문으로 대조한 결과, CAST는 평가 규모에서
이미 이들과 비슷하거나 앞선다. Caspian(학회 8쪽)보다는 확실히 앞선다.

----------------------------------------------------------
Caspian     IEEE MASCOTS 2024, 학회 8쪽
            공간+시간 동시(ILP), 예측기 없음, 용량 하드제약
            3리전 / 합성 200건 / 40시간 / -33.2%

CAST        8리전 / 합성 146,000건 / 2025년 1년 실측 / -56.85~65.93%
            LSTM 예측 + ILP 공간 + 시간 이동
            시뮬레이션 (실배포 없음)


[3] 중요한 발견: "용량"은 더 이상 우리만의 것이 아니다
----------------------------------------------------------
네 편 전부 어떤 형태로든 용량 제약을 다룬다.
  Caspian    - 식(5) 하드 제약
  CASPER     - 탄력적 용량 + 전역 서버 상한
  CarbonFlex - 하드·온라인, 게다가 용량 스윕(Fig.8)까지 했다
  CICS       - VCC로 시간별 상한, 프로덕션 배포

=> "용량을 고려한 연구가 없다"는 주장은 이제 못 쓴다.

그런데 아무도 안 한 게 하나 남아 있다.
  "용량 제약이 없었다면 얼마나 줄었을 것을, 제약 때문에 잃었는가"
  = 무제약 대비 반사실(counterfactual) 비교.
  CarbonFlex조차 안 했다. 자기 알고리즘이 애초에 상한을 안 넘기 때문에
  '무제약 시나리오' 자체를 돌려본 적이 없다.

CAST는 그걸 쟀다.
  이동 가능 작업의 53.6%가 되돌려짐
  시간 이동 기여 9.07%p -> 2.52%p
  캘리포니아 동시실행 41건 = 상한의 3.4배, 연 867시간 초과

=> 기여 문구를 이렇게 바꾼다.
   (X) 용량 제약이 검토되지 않았다
   (O) 용량 제약이 시간 이동에서 앗아가는 몫이 정량화된 적 없다


[4] 지금 바로 고쳐야 할 것
----------------------------------------------------------
순서대로. 1~4는 새 실험이 필요 없다.

1. Caspian 인용 추가 + 기여 #3 문구 좁히기          [문장 수정]
   지금 본문에 Caspian이 한 번도 안 나온다.
   그런데 문단 354가 "두 축 결합 시스템은 보고된 바 없다"로 끝난다.
   Caspian이 정확히 그거다. 아는 심사위원이면 바로 잡는다.

2. 잘못된 직접인용 3개 수정                         [필수]
   직접인용 43개 중 37개는 원문과 정확히 일치한다. 3개가 문제다.
   - 문단 100, 335 : "our current work primarily focuses on
     exploiting spatial variations" -> CASPER 원문에 이 문장 없음.
     실제 문장은 "we focus on exploiting spatial characteristics
     that involves distributing workloads across regions..."
   - 문단 84 : "carbon footprint of a job can be up to 8x higher..."
     -> CASPER 것으로 표기됐는데 원문에 없음. 출처 다시 찾을 것.
   - 문단 151 : "Cluster schedulers, such as Google's Borg..."
     -> Sukprasert 것으로 표기됐는데 원문에 없음.
   심사에서 원문 대조당하면 가장 치명적인 항목이다.

3. 무릎점 자동 알파 검증 표 추가                    [실험 불필요]
   CASPER의 고정 alpha=0.5를 비판해놓고 우리가 더 낫다는 표가 없다.
   데이터는 이미 있다:
     load_balancer/02_프레임워크/results/summary.json
   핵심 한 줄:
     auto의 평균 alpha는 0.508로 고정 0.5와 사실상 같은데,
     지연 6.7ms만 더 쓰고 탄소를 10.7%p 더 줄인다.

4. 기상 예보 누출을 7절 한계에 추가                 [한 문장]
   캘리포니아/텍사스/독일 LSTM 입력이 '미래 실측 날씨 슬라이싱'이다.
   진짜 예보가 아니다. 문단 464가 스스로 경고하는데 한계 목록엔 없다.
   코드로 확인되는 사실이라 발견되면 방어가 안 된다.

5. 6.2절 재서술                                     [해석만 변경]
   LSTM이 1시간 지평에서 지속성 기준선에 0/8로 진다.
   예측 품질의 기여는 전체 절감의 0.14%뿐이다.
   숨기지 말고 발견으로 바꾼다:
   "탄소 인지 스케줄링의 이득은 예측기 품질에 둔감하다"
   그리고 6시간 지평은 8/8로 이기므로:
   "공간 이동엔 예측이 거의 불필요, 시간 이동에만 필요하다"

6. 내부 메모 6건 + "근거 필요" 5건 정리             [반나절]
   문단 111, 344는 이미 해소돼서 그냥 지우면 된다.

7. 용량 스윕 / 되돌리기 스크립트 복원               [하루]

   스크립트가 레포에 없다. 재현 요구받으면 여기가 걸린다.
   새 값을 구하는 게 아니라 논문에 적힌 수치를 재생산하는 것.

8. 스케줄러에 온라인 용량 제약 구현                 [코드+재실행]

[6] 판단이 필요한 것 하나
----------------------------------------------------------
스케줄러에 용량 제약을 넣을 것인가?

넣으면
  헤드라인이 "59.37~65.93% 사이"라는 애매한 구간에서
  하나의 숫자로 확정된다.
  기여가 "측정"에서 "측정+해결"로 올라간다.
  네 편 전부 용량을 다루는 상황에서 우리만 안 다루는 모양새를 면한다.

비용
  코드 변경 자체는 작다.
  compute_time_shift()의 후보 슬롯 루프에
  (리전,슬롯) 점유 카운터를 더해 상한 찬 슬롯을 빼면 된다.
  CarbonFlex도 그리디 리스트 스케줄링이지 ILP가 아니다.
  진짜 비용은 1년치 재실행 쪽이다.

중요한 점
  어차피 [4]-7번(스윕 스크립트 복원)을 해야 한다.
  그 하네스가 생기면 8번은 거의 공짜로 따라온다.
  따로 계산할 일이 아니다.


[7] 이름 문제
----------------------------------------------------------
같은 분야에 CASPER / Caspian / CarbonCast / CarbonFlex 가 이미 있다.
CAST는 CarbonCast와 너무 비슷하고, CASPER/Caspian과 앞 세 글자가 같다.

** 정정 ** 논문 제목은 이미 잘 돼 있다. README만 낡았다.

논문 파일의 현재 제목 (문단 40-41)
  국문: CAST: 리전 용량 제약을 고려한 탄소 인지 시공간 워크로드 스케줄링
  영문: CAST: Carbon-Aware Spatio-Temporal Scheduling

국문 제목이 이미 "리전 용량 제약"으로 시작한다. 잘 잡았다.
낡은 건 README 쪽이다.
  README: Carbon-Aware Scheduling and Traffic routing  <- 옛날 이름

권고: 영문 풀어쓰기에서 한 단어만 바꾼다.
  (현재) CAST = Carbon-Aware Spatio-Temporal
  (변경) CAST = Capacity-Aware Spatio-Temporal

이유
  Carbon-Aware 는 이 분야 논문이 전부 쓰는 말이라 차별점이 안 된다.
  CASPER, Caspian, CarbonFlex, CarbonCast 다 탄소 인지다.
  우리만 있는 건 "용량"이고, 국문 제목은 이미 그걸 앞세우고 있다.
  영문도 맞추면 국문/영문/기여/결론이 한 단어로 꿰인다.
  글자는 C-A-S-T 그대로라 바꿀 게 없다.

  탄소가 빠지는 게 걱정되면 부제로 살리면 된다.
  "Capacity-Aware Spatio-Temporal Scheduling for Carbon Reduction"


[8] 참고 논문에서 가져와도 되는 것 / 안 되는 것
----------------------------------------------------------
가져와도 되는 것 (정상적인 학술 관행이다)
  - 절 구성 순서 (문제정의 -> 형식화 -> 알고리즘 -> 평가 -> 결론)
  - 그림의 종류 (아키텍처 그림, 입력 탄소 트레이스 그림,
    시간별 배분 그림, 가중치 스윕 그림)
  - 평가 설계 (가중치 스윕, 단계별 어블레이션)
  - 지표 정의식 (CS = 100*(C-C*)/C 같은 것). 인용만 달면 된다.
  - 표기 규약, 한계를 서술하는 방식

가져오면 안 되는 것
  - 문장. 번역해서 쓰는 것도 안 된다.
    카피킬러는 한국어 문자열을 잡으므로 번역문은 검사에 안 걸리지만,
    원문을 아는 심사위원에게 걸리면 그게 더 나쁘다.
  - 그들의 수치를 우리 것처럼 쓰는 것
  - 그림 이미지 자체

실무 규칙
  구조는 베끼고 문장은 직접 쓴다.
  그리고 베낀 구조는 밝힌다.
  "평가 구성은 Caspian[x]의 방식을 따랐다"라고 쓰면
  그건 표절이 아니라 비교가능성 확보다. 오히려 점수를 딴다.


[9] 절 구조를 바꾸기로 함
----------------------------------------------------------
(기존 7절)                    (새 구조)
1. 서론                   ->  1. Introduction
2. 배경 지식              ->  1 또는 2로 흡수 (조사중)
3. 풀고자 하는 문제       ->  3의 첫 소절로 흡수 (조사중)
4. 기존 방법 + 한계       ->  2. Related Work
5. 제안하는 방법          ->  3. CAST
6. 검증                   ->  4. Experiments and Analysis
(없음)                    ->  5. Discussion and Limitations  <- 새로 생김
7. 결론                   ->  6. Conclusion
                              Abstract / References 추가

확인할 것
  기록상 7절 구조는 교수님이 정하신 고정 사항이었다.
  바꾸는 게 확정인지 먼저 확인할 것.

바꾸면 좋은 점
  5. Discussion and Limitations 가 독립 절이 되는 게 크다.
  지금은 한계 4가지가 결론 안 문단 848 한 곳에 뭉쳐 있다.
  CAST는 정직하게 밝힐 한계가 많은 논문이라
  (기상 예보 누출 / LSTM 기여 0.14% / 시뮬레이션 / 용량 미구현)
  이걸 펼 자리가 생기는 건 방어에 유리하다.
  약점을 먼저 말하는 논문이 심사에서 덜 맞는다.

주의
  절이 하나 늘면 분량도 는다.
  KCI 분량 제한을 먼저 확인하고 시작할 것. (조사중)

[11-1] ** 정정: 절 구조는 5단이 표준이다 **

앞에서 "5. Discussion and Limitations 독립 절이 좋다"고 적었는데

실제로 제일 흔한 구성 (5단)
  1. 서론
  2. 관련 연구
  3. 제안 기법
  4. 실험 및 분석
  5. 결론

6단을 쓰는 경우도 있는데, 추가되는 절이 "논의및한계"가 아니라
"배경(Background)"을 관련연구에서 떼는 식이었다 (TKIPS 1건).

그래서 권고를 바꾼다.
  - 5단으로 간다.
  - 한계는 독립 절로 빼지 말고 "5. 결론" 안에서 확장한다.
    지금도 문단 848(한계4가지) 850(향후과제3가지)이 결론에 있다.
    자리를 옮기지 말고 거기서 늘리면 된다.
  - 국내 관행으로는 마지막 절 제목을 "결론 및 향후 연구"로
    하는 경우가 많다. 그렇게 하면 한계/향후과제가 자연스럽다.

기상 예보 누출 같은 한계는 여전히 반드시 넣어야 한다.
자리가 독립 절이 아니라 결론 안일 뿐이다.

[14] 가정이 많다는 걱정에 대해
----------------------------------------------------------
Caspian 이 실제 쿠버네티스에 돌린 건 sleep 명령이다.
  - k3d = 로컬에 띄운 가짜 클러스터
  - 작업 200건 전부 BusyBox 에 sleep 건 것
  - 각주9: 사용률을 실측 안 하고 요청량 비례로 가정
  - 전력효율 rho = 100/200 상수 가정 (그냥 정한 값)
  - 워크로드 200건도 합성 (Poisson, U(1,5))
  - 탄소 데이터 40시간 한 구간

우리 P = 1kW 가정과 Caspian 의 rho 가정은 같은 종류다.
우리가 더 나쁘지 않다. 탄소는 오히려 우리가 1년치 실측 8리전이다.

진짜로 우리보다 앞선 건 둘뿐이다.
  CarbonFlex (AWS 실배포 + 실트레이스 3종)
  CICS (구글 프로덕션)
이 둘은 못 따라간다. 따라갈 필요도 없다.

** 진짜 약점은 하나다 **
  "가정이 많다"가 아니라 "합성 워크로드 파라미터에 근거가 없다"이다.
  문단 566에 이미 (근거 필요) 메모가 붙어 있다.
    - 리전당 하루 50건
    - k 비율 3:2:1:1:3

  해결은 실트레이스로 갈아타는 게 아니다.
  공개 트레이스(Azure, Alibaba, Google cluster trace)의
  발표된 통계를 인용해서
  "우리 생성기는 이 분포를 따랐다"로 만들면 된다.
  실험을 다시 할 필요 없이 인용만 붙이는 일이다.

바로잡을 것
  각 나라 12개는 job 개수가 아니라 동시 실행 상한이다.

[18] 시뮬레이션 걱정에 대한 답 — 방어 논리 확보
==========================================================
Sukprasert(EuroSys 2024)는 실배포 없이 트레이스 분석만으로
EuroSys 에 실렸다. EuroSys 는 우리 목표인 KCI 보다 훨씬 높다.

** 중요: 그 논문은 "실배포 안 한 게 한계"라고 안 쓴다. **
아예 자기를 시스템 논문이 아니라 측정/분석 논문으로 포지셔닝한다.
  - 제목부터 "On the Limitations of..."
  - 초록: "we conduct a detailed data-driven analysis to
    understand the benefits and limitations..."
  - 규모를 기여로 내세움: "123 regions worldwide... over
    three years (2020-2022)"
  - 선행연구를 이렇게 비판: "most analyses focus on a specific
    setting... using a small number of geographical regions"

즉 논법이 이렇다.
  "123리전 x 3년 규모의 비교는 실배포로는 애초에 불가능하다.

[20] 식을 6개에서 3개로 줄인다

아까 식 (12)~(17) 여섯 개를 잡았는데 너무 많다.
이미 (1)~(11)이 있는데 여섯 개를 더 얹으면 읽는 사람이 지친다.

남길 것 3개
  가용 자리   a_r(t)     용량의 정의라 필수
  희망 집합   P_r(t)     "지금 돌고 싶은 작업들"
  우선순위    rho_j(t)   자리 부족할 때의 규칙

빼는 것 (수도코드에 한 줄씩 녹임)
  대기 집합 Q(t) / 윈도우 W_j(t) / 선택 절차 S_r(t)
  * W_j(t)는 이미 5.5절 문단 496에 정의돼 있어서 새 식이 필요 없다.

** 그리고 좋은 발견 **
가용 자리 식은 이미 논문에 있는 식 (3)을 뒤집은 것이다.
  식 (3)   |{ j : r(j)=r, tau_j <= t < tau_j+d_j }| <= floor(eta*cap_r)
  새 식     a_r(t) = floor(eta*cap_r) - |{ ... }|
같은 말이다. 그래서 이렇게 쓸 수 있다.

  "5.2절에서 식 (3)으로 선언했으나 구현하지 않았던 제약을
   이 알고리즘이 실제로 강제한다."

진짜 새 식은 두 개뿐이다. 부담이 거의 없다.

[21] 회계가 두 개 있다 — 알아둘 것
==========================================================
summary.json 은 옛날 버전이 아니다. (내가 처음에 잘못 말했음)
CSV 의 carbon_g 합계와 7개 행 전부 정확히 일치한다.

  로드밸런서 회계 : 실행 구간을 적분        -> summary.json, CSV
  스케줄러 회계   : 정시 단위 빈 평균       -> 논문 표2, alpha 표

둘 다 맞는 계산인데 방식이 다르다. 차이는 최대 0.5%.
alpha=1.0 행만 51kg(0.5%) 차이나는 이유:
  alpha=1 에서 작업 실행시간 중앙값이 78.5초로 짧아진다(0.75는 91.4초).
  짧은 작업은 "한 시간 안에서 어디 놓이냐"에 민감해서 차이가 커진다.
  오류가 아니다.

** 논문은 스케줄러 회계로 통일돼 있다. 표2도 alpha 표도 그것. **
그러니 alpha 표에는 재계산한 숫자를 쓴다. ([17] 참고)

주의: 나중에 누가 재현성 확인하려고 summary.json 을 열면
같은 불일치를 또 만난다. 어느 회계를 쓴 숫자인지 각주로 밝히거나
summary.json 을 스케줄러 회계로 다시 써두는 게 낫다.

그림 글자가 PDF에서 선택된다(우리는 안 된다 — 실측 확인).
