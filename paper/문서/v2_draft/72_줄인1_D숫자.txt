[규칙과 방법]
- %와 %p는 stats.json 의 kg 에서 다시 셈: 절감 = 100×(1 − total_carbon_kg/baseline_kg),
  %p = (kg 차) ÷ 그 실행의 baseline_kg × 100, 마지막에 한 번만 반올림.
  기준 kg: 합성 28,625.462 / Azure 213,513.439 / 시드·φ·발생률·정오 변형은 각 실행의 baseline_kg.
- Azure 는 jobs_azure.csv, 합성은 jobs.csv 실행인지, 그리고 예약 ρ·상한·α·예측기가 원고가 말한 조건과 같은지 실행마다 확인.
  같은 지연 짝은 원고 4.1의 정의(실행 시간 가중 평균 왕복 지연, 0.5 ms 안)에 맞는지도 봄.
- 신뢰구간은 analysis/*.json 과 대조. JSON 이 없는 짝 둘(CAST α=0.5375 대 다시 풀지 않는 설계 α=0.5472, 대 빈 리전 α=0.5375)은
  scheduler.analysis_alpha --pair 로 스크래치에 다시 계산(블록 7일, B=2000, 시드 0 — 저장소 스크립트 그대로).
- 작업별 기록(jobs.csv.gz)에서 직접 다시 센 것: 상한 7 기준 기준선 위반, 상한 없음의 초과 시간 리전 몫, 리전별 실행 몫,
  슬롯별 α 몫, 겹침 길이 정확 적분, p99.9, 선행 정책의 프랑스 몫, 시작 확인형 위반 순간의 다른 리전 빈자리.
  재채점(전송 목적지·출발지, 전과정, 프랑스 한쪽, 대칭 화석)은 저장소 스크립트의 식을 그대로 불러 kg 을 다시 냄.
  forecast_checks.json·india_check(인도 제외 MAE), offline/*.json(gap_pp 와 run_kg−lp_kg 재계산 일치)도 대조.
- 스크래치: /private/tmp/claude-501/.../scratchpad/d1/ (all.txt = 비-_buggy 실행 435개 요약, calc.py·rescore.py·jobs1.py 등).
- 출처 경로는 scheduler/data/v2/ 아래 상대 경로. _buggy_1018* 는 보지 않음. 시뮬레이션은 돌리지 않음.
- 판정: 일치 / 반올림 차 / 불일치 / 출처 못 찾음. "일치(… 주의)"는 값은 자료에서 나오나 정의·기간·짝을 적어 두면 좋은 곳.
  문헌에서 옮긴 값(IEA 전력량, Zanotto·Caspian 평가 규모)은 원자료 대조 대상이 아니라 "문헌값"으로 따로 적고 세지 않음.
